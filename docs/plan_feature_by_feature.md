# 기능 하나씩 완성하기 — 개발 방식 계획

2026-11-11. 사용자 요청: "게임이 내가 원하는 방식이 아닌데, 방식을 수정하려고 하니 다른 부분들과 맞지 않고 오류도 많이 생긴다. 기능을 하나씩 완성해 가면서 개발하고 싶다. 지금 소스를 버리지 않고, 이미 만든 것에 더하거나 빼거나 고쳐서 완벽한 게임을 만들고 싶다."

## 1. 문제 (왜 고칠 때마다 다른 곳이 깨지는가)

- **기능이 서로 얽혀 있다.**
  - 진입 한 번에 무전, 진입 허가, 임무, 문, 질문 카드, 정보 안개, 통솔범위가 함께 움직인다.
  - 하나를 바꾸면 그것을 전제로 짠 다른 기능이 어긋난다.
  - 오늘 겪은 예: 원형 메뉴를 없애자 → 문 행동·명령 카드·테스트가 같이 바뀌어야 했다. 우클릭 이동을 지휘관으로 바꾸자 → 지휘관이 문 앞에 서서 대원 클릭을 가렸다.
- **"원하는 방식"이 한곳에 정리되어 있지 않다.**
  - 기획안과 결정 기록(decisions.md)이 여러 번 바뀌었다.
  - 그래서 기능마다 기준이 조금씩 다르다.
- **완성된 기능과 덜 된 기능의 구분이 없다.** 모두 켜져 있어서, 덜 된 기능이 다른 기능의 확인을 방해한다.

## 2. 방식

### A. 정리 (먼저 한 번)

1. **기능 목록표 (docs/features.md)**
   - 게임에 있는 기능을 모두 적는다(약 40개). 기능마다 적을 것:
     - 지금 어떻게 동작하는가 (한두 줄)
     - 어느 파일에 있는가
     - 어떤 기능에 기대고, 어떤 기능에 영향을 주는가 (연결 지도)
     - 그 기능을 지키는 테스트
     - **상태:** ✅ 원하는 대로 / 🔧 고칠 것 / ➖ 뺄 것 / ⏸ 보류(꺼 둠)
   - 상태 칸은 내가 추천을 적고, **사용자가 정한다.**
2. **게임 방식 한 장 (docs/game_flow.md)**
   - 플레이어가 출동부터 디브리핑까지 무엇을 보고 무엇을 누르는지 순서대로 적는다.
   - 기획안과 오늘까지의 결정으로 내가 초안을 쓰고, 사용자가 고친다.
   - **이 문서가 모든 기능의 기준이 된다.**
   - 기획안과 다른 점은 표로 보여 주고 사용자가 고른다(CLAUDE.md 규칙).
3. **기능 스위치**
   - 기능마다 켜고 끌 수 있게 한다(전체 설정 + 시나리오별).
   - ⏸ 보류인 기능은 꺼 둔다. 그래서 완성 중인 기능을 방해하지 않는다.
   - ➖ 뺄 기능은 먼저 꺼 보고, 문제가 없으면 코드에서 지운다.

### B. 기능 하나씩 완성 (반복)

기능 하나마다 아래 순서로 한다. 한 번에 한 기능만 다룬다.

1. **이 기능의 모습을 정한다.**
   - 짧은 표로 정리한다: 플레이어가 하는 것 / 화면에 보이는 것 / 규칙과 수치 / 다른 기능과 만나는 곳.
   - 사용자가 확인한다.
2. **영향 범위를 확인한다.**
   - 연결 지도로, 이 기능을 고치면 영향받는 기능과 테스트를 먼저 적는다.
   - 깨질 곳을 미리 알고 고친다.
3. **고친다.** 지금 코드에 더하거나 빼거나 고친다. 새로 짜지 않는다.
4. **확인한다.**
   - 관련 테스트를 돌린다.
   - 이 기능만 켠 작은 확인용 시나리오에서 화면을 찍어 내가 먼저 본다.
5. **사용자가 해 본다.** "됐다"면 기능 목록표에 **완성 ✅** 표시를 하고 다음 기능으로 간다.
   - 완성된 기능을 나중에 고치면, 연결된 완성 기능을 다시 확인한다.
6. **전체 테스트는 커밋 뒤 뒤에서 돌린다** (tools/test_bg.ps1).

### C. 기능 순서 (가운데에서 바깥으로)

먼저 완성된 기능 위에 다음 기능을 올린다.

1. 화면·카메라·층 보기
2. 현장지휘관 (이동·둘러보기·지휘소)
3. 차량 도착·배치
4. 대원 선택·이동·진입 (진입구·진입 허가·층·계단·방)
5. 인명검색·구조·집결지
6. 수관·방수·물
7. 화재 (번짐·단계)
8. 연기·시야(정보 안개)·열화상
9. 질문 카드
10. 무전·보고·전술상황판
11. 안전 (공기·RIT·인원점검·철수)
12. 지휘권 선언·최초 상황보고·전략
13. 구급 (분류·처치·이송)
14. 평가·디브리핑·다시 하기
15. 스테이지를 하나씩 확장 (주택 → 필로티 → 아파트 → 고층 …)

튜토리얼은 마지막에 완성된 기능들로 만든다. 기능 하나가 완성될 때마다 튜토리얼 한 단계를 붙인다.

## 3. 작업 방식 (2026-11-11 결정, 그대로)

- 한 번에 작업 하나 → 관련 테스트만 → 사용자 확인 → 다음.
- 질문이 필요하면 묻는다. 특히 기능의 모습(B-1)과 기능 목록표의 상태(A-1)는 사용자가 정한다.

## 4. 첫 작업

**A-1 기능 목록표**를 만든다.

- 나는 코드를 읽고 기능마다 동작·파일·연결·테스트와 추천 상태를 적는다.
- 사용자는 상태 칸만 정하면 된다.
- 그다음 A-2 게임 방식 한 장으로 넘어간다.
